## Сценарий

Сценарий повторяет базовый путь Cal.com. Там владелец создаёт тип встречи в разделе «Ссылки», гость записывается на публичной странице (календарь, свободное время, форма с именем и email), а запись появляется у владельца в разделе «Бронирования → Предстоящие». Регистрация, внешние календари и уведомления Cal.com в проект не переносятся.

1. Владелец создаёт тип встречи и указывает название, описание и длительность.
2. Гость открывает приложение без регистрации и выбирает тип встречи.
3. Гость выбирает день в календаре на ближайшие 14 дней, и приложение показывает свободные слоты этого дня; каждый слот длится столько же, сколько выбранный тип встречи.
4. Гость выбирает слот и подтверждает запись; приложение сохраняет запись, и это время перестаёт быть свободным для всех типов встреч.
5. Владелец открывает список предстоящих встреч и видит новую запись среди встреч всех типов.

## Требования

### Правила записи

- Окно записи занимает 14 календарных дней и сдвигается с течением времени.
- Одно и то же время нельзя занять дважды, даже разными типами встреч; частичное наложение интервалов тоже запрещено, в том числе для двух одновременных запросов.
- Следующая встреча может начинаться в момент окончания предыдущей.
- Начало окна (сегодня или завтра), часы работы владельца, часовой пояс, шаг между началами слотов и данные, которые гость указывает при записи, фиксируются в спецификации.

### Ограничения

- В приложении нет авторизации и личных кабинетов: владелец один и задан заранее.
- В приложении нет интеграций с внешними календарями.
- Приложение собирается в Docker-образ и запускается в контейнере.
- Данные можно хранить в памяти процесса или в базе; сохранение после перезапуска не входит в приёмку. Если данные хранятся в памяти, README должен предупреждать, что перезапуск сбрасывает записи.

### API

- Обязательны TypeSpec-контракт, сгенерированная из него OpenAPI-спецификация и клиентский SDK для фронтенда, сгенерированный из OpenAPI. До выбора стека нужно проверить, что для языка фронтенда есть такой генератор.
- Серверные типы и маршруты генерируются, если фреймворк это поддерживает; иначе бэкенд реализуется по контракту и проверяется тестами.
