# Календарь звонков

Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарий

Сценарий повторяет базовый путь Cal.com. Там владелец создаёт тип встречи в разделе «Ссылки», гость записывается на публичной странице (календарь, свободные слоты, форма с именем и email), а бронирование появляется у владельца в разделе «Бронирования → Предстоящие». Регистрация, внешние календари и уведомления Cal.com в проект не переносятся.

1. Владелец создаёт тип встречи и указывает название, описание и длительность.
2. Гость открывает приложение без регистрации и выбирает тип встречи.
3. Гость выбирает день в окне бронирования (ближайшие 14 дней), и приложение показывает свободные слоты этого дня; каждый слот длится столько же, сколько выбранный тип встречи.
4. Гость выбирает свободный слот и подтверждает бронирование; приложение сохраняет бронирование, и слоты, которые с ним пересекаются, перестают быть свободными для всех типов встреч.
5. Владелец открывает предстоящие бронирования и видит новое бронирование среди бронирований всех типов встреч.

## Требования

### Правила бронирования

- Окно бронирования занимает 14 календарных дней и сдвигается с течением времени.
- Бронирования не могут пересекаться, даже если у них разные типы встреч; частичное наложение интервалов тоже запрещено, в том числе для двух одновременных запросов.
- Следующее бронирование может начинаться в момент окончания предыдущего.
- Начало окна бронирования (сегодня или завтра), часы работы владельца, часовой пояс, шаг между началами слотов и данные, которые гость указывает при бронировании, фиксируются в спецификации.

### Ограничения

- В приложении нет авторизации и личных кабинетов: владелец один и задан заранее.
- В приложении нет интеграций с внешними календарями.
- Приложение собирается в Docker-образ и запускается в контейнере.
- Данные можно хранить в памяти процесса или в базе; сохранение после перезапуска не входит в приёмку. Если данные хранятся в памяти, README должен предупреждать, что перезапуск сбрасывает бронирования.

### API

- Обязательны TypeSpec-контракт, сгенерированная из него OpenAPI-спецификация и клиентский SDK для фронтенда, сгенерированный из OpenAPI. До выбора стека нужно проверить, что для языка фронтенда есть такой генератор.
- Серверные типы и маршруты генерируются, если фреймворк это поддерживает; иначе бэкенд реализуется по контракту и проверяется тестами.

## Стек

- Бекенд: TypeScript, Node.js 26, Fastify.
- Фронтенд: TypeScript, Vite, React, React Router, Mantine.
- Тесты: Vitest, во фронтенде с Testing Library и jsdom.
- Проверки: oxlint, oxfmt, jactionlint и Git-хуки через hk.
- Окружение: mise фиксирует версии инструментов, задаёт задачи и фоновые серверы.

Цепочка контракта проверена на этих версиях: TypeSpec 1.18 генерирует OpenAPI, а `@hey-api/openapi-ts` 0.99 генерирует из него клиентский SDK на TypeScript.

## Установка

Нужен [mise](https://mise.jdx.dev/getting-started.html). Он ставит Node.js и остальные инструменты, npm-зависимости и Git-хуки.

```bash
git clone https://github.com/Yaro812/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install
```

## Использование

<!-- Добавьте запись asciinema — именно это смотрит работодатель -->

Запустить бекенд и фронтенд в фоне и узнать их адреса:

```bash
mise daemons start
mise daemons urls
```

В основной копии репозитория бекенд отвечает на http://localhost:3000/api/health, а фронтенд открывается на http://localhost:5173 и проксирует `/api` на бекенд.

Остановить серверы:

```bash
mise daemons stop
```

Запустить все проверки (линтеры, сверку OpenAPI с TypeSpec, типы, тесты); GitHub Actions запускает ту же команду на каждый push:

```bash
mise run check
```

Остальные задачи показывает `mise tasks`.
